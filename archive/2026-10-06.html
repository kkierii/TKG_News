Langflow scores 9.9 for OS command injection through MCP server config, reachable with no account on its documented default
CVE-2026-105697, GitHub as CNA · published 5 October 2026, 20:16 UTC
CVE-2026-105697 was published on 5 October 2026 at 20:16 UTC with GitHub as the assigning CNA, scored 9.9 critical on CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H and classified CWE-78, OS command injection. Before Langflow 1.10.3, the MCP stdio transport launched whatever command and arguments a user placed in an MCP server configuration — no allowlist, and wrapped in bash -c "exec {command} ...". The record states the command runs on the Langflow host as the Langflow process user as soon as Langflow tries to connect to that server, which includes merely listing servers or loading tools, and that it runs even when the interface then reports that the stdio server failed to start. Affected are langflow from 1.1.2 to before 1.10.3, langflow-base from 0.1.2 to before 0.10.3, and lfx before 1.10.3; the fixes are 1.10.3, 0.10.3 and 1.10.3.
The default configuration removes the authentication requirement entirely. The CVSS vector says PR:L, privileges required — and the record then explains why that understates it: “With the default LANGFLOW_AUTO_LOGIN=true, GET /api/v1/auto_login hands out a token without credentials, so on an exposed instance running the default configuration this is reachable without an account.” Langflow documents AUTO_LOGIN as a development-only setting. With it disabled, the record says any authenticated non-admin user can still exploit it. Two reachable paths are named: the MCP server settings screen, including POST and PATCH to /api/v2/mcp/servers/{server_name}, and building a flow with the MCP Tools component.
One of five Langflow records published within forty minutes, and two of them conflict. CVE-2026-105740 carries the same 9.9 score and the same vector, describes the same bash -c path, and says it is fixed in 1.9.0 — affecting versions before 1.9.0 only. CVE-2026-105697 says versions up to 1.10.2 are affected. Both cite pull request 12290; 105697 also cites pull request 14036. The straightforward reading is that 1.9.0 fixed one route and the component route survived to 1.10.3, but neither record says that, and as filed the two give different answers to which version is safe. Also published that evening: CVE-2026-105741, an X-Forwarded-For spoof that defeats the local-only check on the MCP install endpoint and writes a client config file to disk (7.1, versions 1.5.0 to before 1.10.3), plus CVE-2026-105699 and CVE-2026-105698 at 7.1 and 5.4.
Two more MCP records the same day, from two other vendors. Grafana published CVE-2026-89039 against mcp-k6 at 6.5 (CWE-22 and CWE-424): a caller who can invoke the convert_playwright_script prompt passes a bare file path and receives any file the server user can read, with SSH keys and cloud credentials named in the advisory, and the working-directory restriction on @-prefixed paths defeated by a symlink. Affected 0.3.0 to 0.7.0, finder credited as bebold6133. And CVE-2026-105762 assigned an unauthenticated SSRF in Dify’s /console/api/remote-files/upload at 8.3 — though see the Brief below, because that one is not new.
What none of these records says. No exploitation in the wild is reported for any of them, and no record carries a solutions, timeline or credits field except Grafana’s finder credit. The Langflow GitHub advisory page itself shows a publication date of 28 September, ahead of the 5 October CVE records. We did not run any proof of concept, and the 9.9 and the auto-login description are the CNA’s own characterisation, read from the CVE record rather than reproduced by us.

Grafana assigns a CVE to an MCP prompt that returns any file the server can read, including SSH keys
Grafana Labs security advisory, CVE-2026-89039 · published 5 October 2026
Grafana, acting as its own CNA, published CVE-2026-89039 against mcp-k6 on 5 October at 14:52 UTC, scored 6.5 medium on CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N. A caller able to invoke the convert_playwright_script prompt can pass a bare file path as the playwright_script argument and receive the contents of any file readable by the user running the server; the advisory names SSH keys and cloud credentials in that user’s home directory. The working-directory restriction that applies to @-prefixed paths can be bypassed with a symbolic link inside the working directory pointing outside it. The affected range is 0.3.0 to 0.7.0, the finder is credited as bebold6133 (Researcher), and the weaknesses are listed as CWE-22 and CWE-424.

The record is thinner than the score suggests. It carries no workaround and an empty solutions field, so the fixed version comes from the advisory page rather than the CVE record. CWE-424 appears as a bare identifier with no description text. No in-the-wild exploitation is stated anywhere in the record; the “Exploitation: none” reading in circulation is CISA’s own SSVC assessment as of 5 October, not Grafana’s finding.

Preprint: public vulnerability benchmarks cannot separate prior exposure from capability, authors test on undisclosed bugs
arXiv 2610.06584 (Heldt, Turk, Landolt, Fritz) · submitted 5 October 2026, 16:00 UTC
The abstract argues that release decisions for frontier AI systems increasingly rely on cyber capability benchmarks, while public vulnerability benchmarks can expose agents to already-published advisories, exploits and fixes — making prior exposure indistinguishable from capability. The authors evaluate open-weight and proprietary models on exploit generation, vulnerability repair and subsequent attacks in five nonpublic software environments, including vulnerabilities they say they privately disclosed while those remained unpatched, and state that deterministic graders developed and reviewed by researchers, not LLM judges, set the task scores. Repair scores exceed attack scores in two of the five nonpublic environments and fall below them in three. After an initial exploit is stopped, another exploit succeeds in 92 of 524 defender test intervals.

What is not established. This is an 8-page preprint with one figure and no peer-review status shown, the experiments are the authors’ own, and we read the arXiv API record and abstract rather than the paper. The abstract does not name a single model tested, so the “substantial variation across systems” it reports cannot be attributed to any vendor. The authors describe the 524 intervals as non-independent, so that figure is not 524 separate trials.

Research
Preprint: twenty deepfake detectors fall from 99.5% to 76% accuracy against newer generators, and below 2% under attack
arXiv 2610.05870 (Hashmi, Elsayed, Alam, Poppi, Lukas) · submitted 5 October 2026, 06:36 UTC
The authors evaluate twenty deepfake detectors against ten generators released over the last four years and report accuracy decreasing over that span, from a near-perfect 99.5% to 76%. Adversarial perturbations reduce every baseline detector to below 2% accuracy, which the abstract describes as effectively inverting the detector’s assigned label. Their argument is that content alone cannot reveal provenance, because a generator can reproduce authentic content exactly through memorisation; they instead propose a calibrated prediction of whether authenticity is plausibly deniable, where a faithful reconstruction by any known generator establishes deniability. At a calibration admitting at most 1% of generated content wrongly certified, they report most baselines reach near-zero recall, including the strongest at 93% accuracy. Of 3,000 Reddit images, 1,116 resist reproduction by a 2022 generator but only 55 to 79 resist 2024 generators.

What is not established. A preprint with no peer-review status shown; the experiments are the authors’ own and we read the abstract rather than the paper. The authors themselves bound the robustness claim to the evaluated bounded-perturbation attack space and state it does not cover arbitrary adversarial transformations. The abstract names none of the twenty detectors or ten generators, and does not say how the 3,000 Reddit images were selected or labelled.

Research
Preprint: a manual audit finds roughly 60% of correct LLM vulnerability verdicts carry fabricated or unverifiable claims
arXiv 2610.06366 (Hu, Ahir, Ni, Jia) · submitted 5 October 2026, 14:03 UTC
The abstract reports that the authors’ manual audit found approximately 60% of correct vulnerability verdicts accompanied by fabricated or unverifiable claims, and that free-form chain-of-thought explanations let reasoning errors evade LLM-as-a-judge evaluation. Their framework, VERA, has the model emit a Structured Reasoning Record encoding tracked pointers, memory operations and state transitions in machine-readable fields, which a multi-stage judge audits against eight reasoning failure modes using deterministic checks, reserving model calls for semantic interpretation. They report that reasoning flaws occur in correct verdicts just as frequently as in incorrect ones, and that VERA exposes 87% of reasoning errors that free-form LLM-as-judge systematically misses.

What is not established, and the 60% needs care. The abstract says “approximately”, so it is not a precise figure, and it gives no sample size, no model names and no dataset for the manual audit that produced it. This is a preprint with no peer-review status shown and no page count in its arXiv record, the experiments are the authors’ own, and we read the abstract rather than the paper.
